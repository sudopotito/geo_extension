# Geo Extension — Maintainer & Agent Notes

Orientation for anyone (human or AI) working on this repository. The README is the user-facing documentation; this file records the invariants, the technical details and the open items.

## What the app does

Turns the native Frappe **Address** form (plus quick-entry dialogs and Address Web Forms) into a cascading, country-aware selector: Country → level 1 → level 2 → … → postal code. Everything is data-driven by per-country datasets; the DocType is never changed.

## Invariants

1. **No schema or layout customisation.** The app must never create Custom Fields or Property Setters and has no install/uninstall hooks. Sites upgrading from ≤ 1.4 are cleaned once by the patch `patches/v2_0/remove_legacy_address_customizations.py` (idempotent; fresh installs never run it because Frappe marks an app's patches as completed on install).
2. **Assist, never restrict.** Fields stay `Data`. Suggestions are attached at runtime (Awesomplete on the plain input). Free text must always be accepted and saved; there is no server-side validation of address values.
3. **Country-agnostic core.** No `if country == "..."` anywhere. Country differences live in `setup/data/countries/<cc>/manifest.json` + CSV files.
4. **Bounded responses.** `get_options` for level > 1 requires a parent; the browser never receives a whole level of a large dataset (Philippine barangays: 42k rows). `MAX_OPTIONS` = 5000, `MAX_SEARCH_RESULTS` = 50.
5. **Soft failure.** Broken or missing datasets make a country "unsupported"; they never raise into the Address form. Loud checking belongs in the validator.
6. **Frappe v15 and v16.** No v16-only APIs; tests import `IntegrationTestCase` with a v15 fallback.

## Architecture

```
 setup/data/countries/<cc>/  manifest.json + level*.csv [+ postal_codes.csv]   data
        │  geo/dataset.py (index + cache) · geo/validate.py
 api.py  get_hierarchy · get_options · resolve · get_postal_codes · search    API (guest, read-only)
        │  HTTP
 public/js/geo_selector.js  client (cached) · GeoCascade · adapters            reusable selector
        │
 address.js · quick_entry.js · address_web_form.js                             integrations
```

## Dataset format

`manifest.json`: `country_code` (= directory name), `name`, `description`, `version`, `source`, `source_url`, `license`, `author`, `updated`, `levels: [{file, label, target_field}]` (top-down, max 6), optional `postal_codes: {file, pattern}`. `target_field` ∈ {`state`, `county`, `city`, `address_line2`}, each at most once.

`level1.csv`: `code,name[,aliases]`; lower levels: `parent_code,code,name[,aliases]`; `postal_codes.csv`: `level,code,postal_code`. Codes are stable source identifiers (PSGC, GeoNames id, URA), aliases are `|`-separated, files are UTF-8 (BOM tolerated).

The validator checks manifest properties, target fields, country code, CSV columns, codes and names, duplicates, orphans, self references, duplicate names under one parent, ambiguous aliases, units without children (warning), postal levels/codes/pattern and duplicate postal rows. Errors fail the command, warnings only with `--strict`.

## Cascade semantics (geo_selector.js)

- `codes[i]` holds the selected unit code per level (`null` = unknown/manual).
- `handle_change(field)` is serialised (a promise chain), then resolves the typed value against the options of that level (names, then aliases); a *different* resolved unit or an empty value clears the levels below; unresolved text keeps their values but drops their codes.
- Postal: exactly one code → fill `pincode` if empty or still equal to `auto_postal`; several → suggestions only; none → retract an auto-filled value. Manual values are never touched. Lookup walks up the ancestors of the deepest selected unit.
- `teardown()` restores labels and suggestion lists; a `_generation` counter cancels superseded `setup()` calls.
- Address form only: Country is moved below Address Type and the level fields are reordered by DOM moves (nothing persisted). Changing the country clears the level values first.

## Commands

```bash
bench --site <site> run-tests --app geo_extension
python -m unittest geo_extension.tests.test_dataset geo_extension.tests.test_validate   # no site needed
node --test "tests/js/test_*.js"
bench geo-extension validate [cc ...] [--strict] [--path DIR]
bench geo-extension list
pre-commit run --all-files
python tools/geonames/build_dataset.py <cc ...> --out geo_extension/setup/data/countries   # see tools/README.md
```

After editing `hooks.py` or Python modules on a bench whose gunicorn runs with `--preload`, run `bench restart --web` and `bench --site <site> clear-cache`, otherwise the workers keep the old code. Browsers cache `/assets/geo_extension/js/*.js`; hard-reload after changing them.

## Known limitations

- GeoNames datasets list populated places with at least 500 inhabitants plus administrative seats (suburbs for AU/NZ); smaller villages are missing and names follow GeoNames conventions. Postal codes from GeoNames attach to a city only when the postal place name matches; otherwise to the parent unit, where they appear as suggestions.
- No postal codes for: GB, SG (postcode identifies a street/building), BR (one generic CEP per municipality), CA (forward sortation areas only), NL (4-digit half only), MX (colonia file too large), AE, SA, EG, NG, NP, PK (no usable file).
- Philippines: highly urbanised cities are listed under the province they lie in, Manila's barangays directly under the City of Manila, and Manila's district-level postal codes are not included (1,474 of 1,642 cities/municipalities have codes).
- Saudi Arabia has two levels (places carry no governorate code in GeoNames). Egypt's governorates use customary English names via `names` overrides; its cities keep GeoNames transliterations.
- Web Forms keep their own field order; only labels, suggestions and postal codes are applied. Non-standard Web Forms need the one-line client script from the README.
- Datasets are shipped with the app; updating data means updating the app (or using `geo_extension_dataset_roots`).
- A name edited by hand that matches neither a name nor an alias ends the cascade at that level, by design.
- v15 is verified by importing the app and running the site-independent tests on a v15 bench and by CI; browser checks ran on v16.

## Decisions taken (2026-09)

- No save-time normalisation of typed values, no rate limiting on the guest API, no "unresolved addresses" report (decided against or deferred).
- Datasets: official sources when downloadable (PSGC, data.gov.sg), GeoNames otherwise; builders live outside the installed package. Countries were chosen by where Frappe/ERPNext is most used; VN (2025 province reform), JP and KR (huge or non-Latin postal files) were left out.
- The 1.x `locations` shim and all install hooks were removed for 2.0; cleanup is a one-time patch.

## Ideas for later

- More countries (any GeoNames-covered country is one `countries.json` entry away); official sources for IN (Census/India Post), ID (BPS), BR (IBGE) would beat GeoNames.
- Optional "search everything" box on the Address form using `api.search` (the endpoint exists; no UI yet).
- Dataset updates independent of app releases (a downloadable dataset pack into `geo_extension_dataset_roots`).

`enhancement` → `develop` → `main` (releases are tagged from `main` by semantic-release; the `feat!` commit makes the next release 2.0.0). Keep `develop` and `main` free of direct commits.
